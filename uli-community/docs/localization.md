# Localization

## Introduction

This project uses **Gettext** for internationalization (i18n) and localization (l10n). Gettext is the standard GNU translation system, and Phoenix ships with first-class support for it via the `gettext` Elixir library.

### How Gettext works (the short version)

You mark strings in your source code with a `gettext()` call:

```elixir
gettext("Log in")
```

At runtime, Gettext looks up the current locale and returns the translated string for that locale. If no translation exists, it falls back to the original string — so the app stays functional even when a translation is missing.

Translations live in `.po` files under `priv/gettext/`. Each locale gets its own directory:

```
priv/gettext/
  en/LC_MESSAGES/
    default.po     ← English (fallback, usually left empty — msgid IS the string)
    errors.po      ← Ecto validation error translations
  hi/LC_MESSAGES/
    default.po     ← Hindi translations
    errors.po      ← Hindi Ecto error translations
```

A `.po` file is a flat list of translation pairs:

```po
msgid "Log in"
msgstr "लॉग इन करें"
```

`msgid` is the original string from the source code. `msgstr` is the translation. When `msgstr` is empty, the `msgid` itself is shown as a fallback.

There is also a `.pot` file (Portable Object Template) — `priv/gettext/default.pot`. This is an auto-generated master list of every `msgid` extracted from the source. You never edit `.pot` files by hand; they are regenerated by the mix tasks described in the Housekeeping section.

### How the locale is set at runtime

Two mechanisms work together:

1. **`UliCommunityWeb.Plugs.Locale`** — runs on every HTTP request through the browser pipeline. It reads the `:locale` key from the session and calls `Gettext.put_locale/2` to activate it for the current process. It defaults to `"en"` if nothing is stored.

2. **`UliCommunityWeb.LocaleOnMount`** — runs as an `on_mount` hook for every LiveView session. LiveViews communicate over a persistent WebSocket connection that bypasses the Plug pipeline, so the locale must be re-applied when the LiveView mounts. This hook reads the locale from the session map and calls `Gettext.put_locale/2`.

A user switches language by clicking the **EN | हिं** toggle in the navigation bar, which hits `GET /locale/:locale`. The `LocaleController` writes the chosen locale to the session and redirects back to `/`. All subsequent requests and LiveView mounts pick it up automatically.

## How-to: Writing localizable code

### Always use `gettext()` for user-facing strings

Any text that a user will read belongs inside a `gettext()` call. Never embed a bare English string in a template or LiveView render function.

**In `.heex` templates:**

```heex
<%!-- wrong --%>
<h1>Account Settings</h1>

<%!-- right --%>
<h1><%= gettext("Account Settings") %></h1>
```

**In LiveView `.ex` files** (`gettext` is imported automatically via `use UliCommunityWeb, :live_view`):

```elixir
# wrong
label="New password"

# right
label={gettext("New password")}
```

**In controllers and other modules** — import the Gettext module if it isn't already:

```elixir
import UliCommunityWeb.Gettext

# then use it
put_flash(conn, :info, gettext("Email changed successfully."))
```

### Strings to skip

Not every string needs to be wrapped. Skip:

- Internal error messages that users never see (log lines, exception messages)
- Hard-coded HTML attributes like CSS class names
- Long paragraphs that are not yet ready for translation — wrap them later when translations are available, rather than leaving them partially translated

When you intentionally skip a string, leave a comment so the next developer knows it was a conscious choice:

```heex
<%!-- i18n: long paragraph, deferred --%>
<p>Use Uli to redact slurs and abusive content...</p>
```

### Interpolation (dynamic values inside strings)

When a string contains a dynamic value, use `gettext` with a binding:

```elixir
gettext("Welcome, %{name}!", name: user.name)
```

The `.po` entry will look like:

```po
msgid "Welcome, %{name}!"
msgstr "%{name}, स्वागत है!"
```

Never concatenate strings with `<>` to build a translated sentence — word order differs between languages and concatenation breaks in translation.

### Plural forms

For counts, use `ngettext`:

```elixir
ngettext("1 item", "%{count} items", count)
```

Hindi has different plural rules than English. The `.po` entry for a plural string uses `msgstr[0]` and `msgstr[1]`:

```po
msgid "1 item"
msgid_plural "%{count} items"
msgstr[0] "%{count} आइटम"
msgstr[1] "%{count} आइटम"
```

### Adding a new locale

1. Run `mix gettext.merge priv/gettext --locale <code>` (e.g., `--locale ta` for Tamil)
2. This creates `priv/gettext/<code>/LC_MESSAGES/default.po` and `errors.po`
3. Add the locale code to the `@supported_locales` list in both:
   - `lib/uli_community_web/plugs/locale.ex`
   - `lib/uli_community_web/controllers/locale_controller.ex`
4. Add a toggle link in `lib/uli_community_web/components/layouts/root.html.heex`
5. Fill in translations in the new `.po` file

## Housekeeping

These two mix tasks keep the translation files in sync with the source code. Run them regularly — ideally before every commit that touches templates or LiveViews.

### 1. Extract new strings

```bash
mix gettext.extract
```

Scans all source files for `gettext()`, `ngettext()`, and `dgettext()` calls and rebuilds `priv/gettext/default.pot`. Any new strings you added will appear in the `.pot` file after this step.

### 2. Merge into locale files

```bash
mix gettext.merge priv/gettext
```

Propagates changes from the `.pot` file into every locale's `.po` files. New `msgid` entries are added with an empty `msgstr`. Removed entries are marked as obsolete (commented out) so translators know they are no longer needed.

You can do both steps in one command:

```bash
mix gettext.extract --merge
```

### 3. Fill in translations

Open `priv/gettext/hi/LC_MESSAGES/default.po` and fill in the `msgstr` for any entry that has an empty translation. Entries added by the merge step will appear at the bottom of the file.

### Recommended pre-commit checklist

Before committing a feature branch that includes new or changed UI text:

1. Run `mix gettext.extract --merge` — ensure no new `msgid` entries appear that you forgot to translate
2. Check `priv/gettext/hi/LC_MESSAGES/default.po` for empty `msgstr` values on any string you intended to translate
3. Commit both the source changes and the updated `.po`/`.pot` files together so the translation state stays consistent with the code

### Checking for untranslated strings

To find all entries in the Hindi `.po` file that are still missing a translation:

```bash
grep -A1 'msgid' priv/gettext/hi/LC_MESSAGES/default.po | grep 'msgstr ""'
```

This prints every `msgstr ""` line — each one is a string the user will see in English even when the Hindi locale is active.
